# Status

Snapshot of where the work stands, for picking it up later. Spec: GitHub issue #1. Branch: `feat/mvp-visualisation`.

## How to run it against the PLC

1. Open `plc/RPP_Visu.sln` in TwinCAT XAE (4026, user-mode runtime `UmRT_Default`, target `169.254.123.103.1.1`, which is this PC).
2. Build, activate the configuration, log in and start the PLC. If the manifest looks stale after an online change, do a cold reset and start again.
3. `corepack pnpm install`, `corepack pnpm build:bridge`, `corepack pnpm --filter @rpp/web build`
4. `cd apps/gateway && node_modules/.bin/tsx src/main.ts --driver ads --ams-net-id 169.254.123.103.1.1 --ads-port 852 --port 8080` (the demo project `Syn_Visu_Demo` runs on port 852; the library project on 851 has no task)
5. Open http://localhost:8080

Without a PLC: `--driver sim` (built-in simulator, same contract).

## Done

- MVP from issue #1: protocol package, gateway (discovery, sum-read snapshots, version checks, reconnect), simulator, React Three Fiber debug UI.
- PLC library `Syn_Visu` (`plc/Syn_Visu`), contract in `docs/plc-contract.md`, **protocol version 14** (3: work area → working area, windows → zones; 4: XTS kinematics, `nMoverId`, `fEncoder` → `fBeltPosition`; 5: Cartesian robot; 6: Delta limit area, zone allocation offset; 7: gripper fingers, tool rotations removed; 8: faults; 9: zone CCS offset, origin shift; 10: product shapes; 11: detectors, zones without kind; 12: XTS tracks of modules with a fault each; 13: generic product client, station; 14: product poses in the conveyor's coordinate system).
- XTS gantry (IDH) and XTS loop (Fxx), issue #3: contract, `FB_VisuXtsGantry` / `FB_VisuXtsLoop`, gateway, scene model, drawing, measure-mode snap points, mover table in the inspector.
- Cartesian robot, issue #4: contract, `FB_VisuCartesian`, gateway, scene model (rails, bridge, carriage, column, gripper head, TCP volume), measure-mode snap points, axis table in the inspector.
- Delta limit area (box in the robot frame, own layer toggle "Limit areas") and zone allocation area / allocation limit (layer zones), with measure-mode snap points.
- Eye button per component in the component tree hides it (a hidden conveyor hides its products and the zones on it); separate "Limit areas" layer toggle; conveyors drawn dark blue.
- Grippers for every kinematics: fingers as cylinders at MCS poses reported by the PLC, products hanging at a finger's grip point (`nFingerId`), finger table in the inspector; the tool rotations (Delta rz, IDH C, Cartesian C/A and tool length) moved into the finger poses. Demo: three different Delta grippers. The simulator has one Delta with a single cup.
- The Syn_Visu copy in the Viersen project is still on protocol 6 (wrappers use IDH C and LUN C) and on the old names; to be updated.
- ADS access through `apps/ads-bridge` (.NET, Beckhoff `TwinCAT.Ads` 7.0.389), because the pure TCP client `ads-client` is rejected by the 4026 user-mode runtime's router (no AMS TCP loopback, no route). `ads-client` remains as `--driver ads-tcp`.
- Delta reports only its TCP; the web derives the arms by inverse kinematics (was: axis angles in protocol version 1).
- Delta drawn like a real robot: base plate, motors, upper arms, parallelogram lower arms, effector with TCP axis triad.
- Measure mode (issue #2, key M): component origin triads, snap points at characteristic points (belt corners, zone corners, Delta base/shoulders/TCP, working area, product corners), frozen measuring points with MCS and local coordinates, the offsets ΔX, ΔY, ΔZ from point to point and CSV copy. Replaced the pointer readout and Shift+click points.
- Product colour legend appears only in a popup while a product is selected.
- Replay buffer (ADR 0011): the browser always keeps the last minute; the icon button right of Record plays it as a recording that saves like any other.
- Recording and playback (ADR 0006): record button in the 3D view records every message of all sources in the browser (about 1.6 MB per minute, 10 min limit), player bar with play/pause, single steps, slider, 0.1× to 2×, "Live", save as `.rpprec` and open again. Selection, inspector, hiding and measuring work in playback. Not yet tried on a panel PC.
- Protocol version 9: every zone has a CCS offset (the robot's conveyor coordinate system, a black dashed line across the zone, snap point, warning outside the zone) and every component an origin shift (`m_SetOriginShift`): the origin triad and local measuring coordinates move there, and a conveyor's belt coordinates count from it. Library 3.3.0. Demo: CCS in every zone, Delta origins 900 mm below the base, the Cartesian infeed counts from the robot's Y = 0.
- Library 3.4.0: `m_LatchProduct(..., vi_e_State, vi_udn_RobotId)` enters a product a robot puts down onto a conveyor as `PLACED`, so it does not show as missed at the belt end. The demo uses it on its outfeeds and tray, and releases products on the Spacing belt as `PLACED`.
- Protocol version 10, library 3.5.0: product types have a shape (`E_VisuProductShape`: box, cylinder with two diameters for round and oval products, rounded box with `fCornerRadius` for pouches); `m_SetProductType(..., vi_e_Shape := BOX, vi_lr_CornerRadius := 0)`. The web draws each shape (placeholders as outlines) and offers the outline's front, back, left and right instead of corners for round and rounded products. Demo: the Delta application mixes five product types (two boxes, a can, an oval, a pouch). Viersen and RPL6 need library 3.5 before they work with this gateway. A product a robot puts down on another conveyor now leaves the register it was picked from (`m_RemoveProduct`); `PLACED` means it lies on that belt.
- Protocol version 11, library 4.0.0: vision system and product sensor (`_FB_VisuVision`, `_FB_VisuSensor`, sharing `ST_VisuDetector`), drawn from bodies they describe (ADR 0007); zones without kind, set by index (`m_SetZone(vi_un_Zone, vi_udn_ConveyorId, ...)`), shared by robots and detectors through `_FB_VisuZoneComponent` / `_FB_VisuRobot`; `m_LatchProduct(..., vi_udn_DetectorId)` names the detector, shown in the product history and the metrics. The TypeScript side became generic: the gateway maps PLC structures by naming convention, `buildScene` runs over one kit per component type, the inspector shows any state through `stateRows`. Simulator: a vision system over the Delta infeed, a light barrier on the Cartesian infeed; demo: the same on the two Delta infeeds. **Migration for Viersen and RPL6 (library 4.0):** remove `vi_e_Kind` from every `m_SetZone` call and add `vi_un_Zone := 1, 2, ...` per robot; `E_VisuZoneKind` no longer exists.
- Protocol version 12, library 5.0.0: XTS tracks are chains of 250 mm motor modules (ADR 0008), straight or quarter curves (`E_VisuModuleKind`), set with `m_SetModule` from the new base `_FB_VisuXtsTrack`; each module can report a fault (`m_SetModuleFault`), drawn red with a label, listed with the component and marked on the timeline (which now finds faults in any list of a state). The web draws every module on its own with a joint; snap points at module boundaries and curve centres; a loop that does not close raises a warning. Simulator and demo: Fxx loop of 2 × 10 straight modules and four quarter curves with a module fault every 20 s, IDH of 6 modules, demo Spacing loop of 2 × 12. **Migration for Viersen and RPL6 (library 5.0):** remove the track parameters from `m_Configure` (gantry `vi_un_ModuleCount`, `vi_lr_ModuleLength`; loop `vi_lr_StraightLength`, `vi_lr_CurveRadius`), call `m_SetModule` per module in track order, replace `m_Perimeter()` by `m_TrackLength()`, and report module faults with `m_SetModuleFault` where the application knows them.
- Versions visible, library 5.1.0 (protocol stays 12): every build has a version (`scripts/app-version.mjs`: `1.2.3` from a CI tag, else `0.1.0+<commit>`, `.dirty` with uncommitted changes) in the zip name, the `VERSION` file, the gateway log, `/health` (`version`) and the status bar; the installer names the version it replaces. The manifest's new last member `sLibraryVersion` (`VISU_GlobalConst.VISU_str_LIBRARY_VERSION`) reaches the `config` message, `/health` (`libraryVersion` per source), the status bar and the protocol version error; libraries before 5.1 simply do not report it. Viersen and RPL6 can take 5.1 without code changes.
- Protocol version 13, library 6.0.0 (ADR 0009): a product names its client generically, `nLastClientId` (the component that made the last change: robot, detector, station) and `ePreviousState`, instead of `nRobotId` and `nDetectorId`; the product history says "released by" / "rejected by", the metrics count per client what it detected, picked, placed and rejected. New component type station (`E_VisuComponentType.STATION`, `ST_VisuStation`, `_FB_VisuStation`): bodies and zones like a detector, its own structure; the body handling moved to the new base `_FB_VisuBodyComponent`, shared with the detectors, and active machine parts now light up too. Simulator and demo: a reject unit at the Delta outfeed rejects every fifth product, its pusher lighting up. **Migration for Viersen and RPL6 (library 6.0):** in every `m_LatchProduct` and `m_SetProductState` call replace `vi_udn_RobotId` and `vi_udn_DetectorId` by `vi_udn_ClientId` (where both were given, the robot); where a robot gives a product back with `vi_udn_RobotId := 0`, pass the robot's id; code that read `nRobotId` or `nDetectorId` of a product reads `nLastClientId`. RPL6's `_FB_SYNVIS_*` wrappers and `_FB_SYNVIS_Handover` need this.
- Protocol version 14, library 7.0.0 (ADR 0010): a product's latch pose is given in its conveyor's coordinate system (pose + origin shift; X along the belt, Rz from the belt's X) instead of the MCS; `m_GetProduct` and `m_MoveProduct` use the same coordinates, the belt travel still moves the product along X. The Delta's TCP axis triad and flange frame keep the MCS axes however the robot is mounted. The demo converts with its own `_FC_DemoMcsToBelt` / `_FC_DemoBeltToMcs` (its belts run along MCS +X). Products can lie on top of each other (`fZ` = height of the one below); simulator and demo show it: the Cartesian robot puts every second product onto the one it put down before, following it along the outfeed. **Migration for Viersen and RPL6 (library 7.0):** convert every `vi_LatchPose` and `m_MoveProduct` pose from the MCS into the conveyor's coordinate system (subtract the conveyor's pose and origin shift, turn by its rotation; `fRz` minus the conveyor's `fRz`), and convert poses read with `m_GetProduct` back where the application needs them in the MCS.
- Performance with many products, phase 0 (measuring; `docs/performance.md`): library 7.1.0 with `VISU_un_MAX_PRODUCTS` = 4800 (protocol stays 14, no code changes for machine projects; larger registers cost memory and, until the bridge reads only the counted entries, ADS bandwidth). `pnpm bench` (gateway cycle, state JSON, receiving, product history, replay buffer, machine scene with 500 to 4800 products), `--sim-products <n>` (simulator buffer belt), `/health` `acquisition` per source (read and map times, state size, products, products read twice or missing from one snapshot), the demo's load test `P_VisuDemoStress` (`DEMO_un_StressProducts`, task execution time). The server turns each message into JSON once for all browsers. Measured on the local 4026 user-mode runtime (results in `docs/performance.md`); not yet on an IPC with a real-time core. Then: the bridge reads only counted entries and, asked for changes, only changed products; the web app gets states in register form (`/ws?changes=1`, ADR 0013); belt products are drawn instanced and get snap points only in measure mode; library 7.2.0 finds products by an index and moves the register with MEMMOVE (no contract change). With about 4900 products the gateway needs about 4 ms per cycle instead of 34, the browser runs at about 70 instead of 12 frames per second, and the PLC task at 4000 products averages 87 instead of 144 µs.
- Library 8.0.0 (protocol stays 14): `m_Register` has no `vi_str_Path` any more; every component takes the symbol path of its `vo_Visu` from its own device tree path (attributes `reflection` and `instance-path` in `_FB_VisuComponent`), leaving out the first `VISU_un_INSTANCE_PATH_SKIP` segments (default 2: TwinCAT project and PLC project). Machine projects remove `vi_str_Path` from every call. Checked on the demo PLC: all 20 components discovered without errors. Methods have no default values any more and every call lists all inputs (TwinCAT 4024 compiles only full calls; the 4026 compiler then reports incomplete ones too); the library itself called `m_SetBody` incompletely four times.
- Protocol version 15, library 9.0.0: zones are bounded across the belt too. `ST_VisuZone.fStartY` / `fEndY` (`m_SetZone(..., vi_lr_StartY, vi_lr_EndY)`) are the zone's sides in the conveyor's coordinate system, in any order; equal values span the whole belt width. The scene draws the zone area, the allocation area, the CCS line and the snap points between them, clipped to the belt with a warning. Simulator: Delta 1 places in a 200 mm lane in the middle of the outfeed; demo: the Delta pick zones cover only the 260 mm lane the products come in on. **Migration for Viersen and RPL6 (library 9.0):** add `vi_lr_StartY := 0, vi_lr_EndY := 0` to every `m_SetZone` call (whole belt width), or the lane a component actually uses.
- Several PLCs in one view (ADR 0005): a gateway reads a list of `sources` (AmsNetId + ADS port, other IPCs over an ADS route set up in TwinCAT) and the web app merges them into one scene. Ids unique per source; per-source loops with 5 s reconnect wait, per-source interpolation; an unreachable source stays visible but faded; components grouped per source in the tree; status bar "PLC n/m online" with a source list, a red note when embedded. `install.ps1 -AmsNetId`. Tried with two sources on the local demo runtime (same ids) and one unreachable IPC; not yet with a second IPC.
- Touch and HMI: one app for mouse and touch, embeddable in TwinCAT HMI over http (`?embedded` hides title and status bar, `docs/deployment.md`). Finger-sized controls and larger type on touch screens (`pointer: coarse`); collapsible side panels (open from 1600 px, remembered per device); camera buttons with view icons in the 3D view (top, front, side, iso; zoom by pinch or wheel); a tap selects only without camera drag; in measure mode one finger shows the snap point under it (name above the finger) and sets it on release, two fingers move the camera; fault messages shown in the component list instead of a tooltip; copy buttons hidden without clipboard; page zoom, double-tap zoom and context menu off; render resolution capped at 1.5 device pixels per CSS pixel. Not yet tried on a real panel.
- Gateway re-runs discovery every second (`--config-recheck-ms`), so configs changed live in the PLC appear without bumping `nConfigVersion`.
- Demo in its own PLC project `plc/Syn_Visu_Demo` (one program per application, `P_VisuDemoDelta` ... `P_VisuDemoSpacing`, called by `P_VisuDemo`) and in the gateway simulator: four independent applications side by side, all conveying along +X from X = 0: Delta (two infeeds, one outfeed, three Deltas in a row; Y = 0..1000), Fxx (irregular infeed evened out onto its outfeed; Y = 2500) and IDH (four movers picking in batches from its infeed onto a tray belt; Y = 4100..4850) and Cartesian (picks from its infeed, turns by C = −90°, tilts by A while lowering, places onto its outfeed; Y = 6500..7300). The PLC demo has a fifth one, Spacing (Y = 9000, not in the simulator): an XTS loop under one belt pushes products arriving with random gaps along the belt and hands them back with a constant pitch of 200 mm.
- PLC API: `FB_VisuConveyor` and `FB_VisuDelta` (base `FB_VisuComponent`) with methods replace the helper functions; library version 2.0.0. The ADS contract is unchanged.
- PLC code follows the company guideline (`docs/plc-coding-guidelines.md`), library version 3.0.0: `_FB_Visu*` FBs, `m_` methods, `vi_`/`vo_`/`vio_` inputs and outputs, `Temp` method locals, `VISU_GlobalConst` / `VISU_GlobalConst_Param` with upper-case constants, copyright and help headers. The contract structure is the FB output `vo_Visu` (manifest paths end in `.vo_Visu`). Structures, members, enums and `GVL_Visu.stManifest` are unchanged, so the protocol stays at version 7. Faulted parts glow red, a label with the message hangs above them (layer toggle "Fault labels"), the component list marks them with ⚠ and the messages as tooltip, the inspector shows them and a Fault column for movers. ## Decisions changed during implementation

The spec in issue #1 is updated to these. The hard-to-reverse ones are recorded in `docs/adr/`:

- ADS via the .NET bridge instead of `ads-client` (ADR-0001).
- Delta state is TCP only, protocol version 2 (ADR-0002).
- The manifest `GVL_Visu.stManifest` is declared by the application, not by the library (ADR-0003).
- Third browser message kind `status`; full discovery repeated every second; a rejected product past the belt end is hidden instead of flagged as missed.

Domain terms are defined in `GLOSSARY.md`.
