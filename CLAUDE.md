## Commands

pnpm monorepo (pnpm 12 via corepack; prefix with `corepack` if `pnpm` is not on PATH).

- `pnpm install`
- `pnpm test`: all Vitest projects. Single file: `pnpm vitest run apps/web/test/scene-model.test.ts`. Single test: add `-t "<name>"`.
- `pnpm typecheck`: `tsc` in every package
- `pnpm test:e2e`: builds the web app and runs the browser tests in `apps/web/e2e/` (Playwright, separate from `pnpm test`); the gateway runs with the simulator on :8090 and serves `dist`. On Windows it uses the installed Edge, elsewhere `E2E_CHANNEL=chromium` after `pnpm exec playwright install chromium`.
- `pnpm dev:gateway`: gateway with the simulator on :8080
- `pnpm dev:web`: Vite dev server that proxies `/ws` to the gateway (override with `GATEWAY_URL`)
- `pnpm build`: builds `apps/web/dist`. `pnpm build:bridge`: builds the .NET ADS bridge (`apps/ads-bridge`, needs the .NET 9 SDK).
- `pnpm start -- --driver ads --ams-net-id <id>` serves the built app plus the WebSocket on one port (`--help` lists the options; `--config <file>` reads them from JSON, flags win).
- `pnpm package`: builds the self-contained Windows package for IPCs, `dist/rpp-visualisation-<version>-win-x64.zip` (Windows, .NET SDK). Deployment: `docs/deployment.md`, ADR 0004; install scripts in `deploy/windows/`.

## Architecture

A read-only web visualisation of packaging machines. It configures itself from what the PLC reports. Spec: GitHub issue #1.

- `packages/protocol`: the neutral data model (zod schemas plus types) shared by gateway and web, and the Delta kinematics. All values are MCS: mm, degrees, Z up. A Delta reports only its TCP; the web derives the arms by inverse kinematics. XTS gantries (e.g. IDH) report their Z axis and per mover track position, X, C and gripper; XTS loops (e.g. Fxx) report per mover the position along the loop. Cartesian robots report their X, Y, Z axes and gripper. Deltas may have a limit area (box in the robot frame); every zone may have an allocation offset. Every kinematics may define gripper fingers (cylinders) whose poses the PLC reports absolute in the MCS; tool rotations exist only through them, and a picked product hangs at its `fingerId`. Every component and every XTS mover may report a fault with a message. Every zone has a CCS offset (the robot's conveyor coordinate system on that belt) and every component an origin shift: where its coordinate system lies relative to its pose; a conveyor's belt coordinates count from it. Product types are boxes, cylinders (two diameters: round or oval) or rounded boxes. Zones belong to robots and detectors alike and have no kind. Detectors (vision system, product sensor) are drawn only from the bodies their PLC function block describes (box, cylinder, frustum with a role), so the web needs no code per detector (ADR 0007); a product names the detector that latched it (protocol version 11). Adding a component type: `docs/adding-a-component.md`.
- `apps/gateway`: Node + TypeScript, run with tsx.
  - `createGateway` reads one PLC source (AmsNetId + ADS port): discovery (manifest at `GVL_Visu.stManifest` → protocol version check → type check per entry → read `stConfig`) and cyclic sum-reads of every `stState` together with `nConfigVersion`. It emits `status` / `config` / `state` messages, each with its `sourceId`, and waits `RECONNECT_MS` after a failure. The server fans them out over the WebSocket and answers `GET /health` (per source connected / last error / time of the last state; 200 or 503) from them (`health.ts`). Several sources (other IPCs over ADS routes, ADR 0005) each get their own gateway and loop; `combineGateways` merges their messages for the server. Manifest ids are unique only per source.
  - **Seam:** `SymbolAccess` (read / typeOf / sumRead). Adapters:
    - `AdsBridgeSymbolAccess` (`--driver ads`, default for real PLCs): spawns `apps/ads-bridge` (the self-contained `AdsBridge.exe` when packaged, else the dll through `dotnet`; see `bridgeLaunch`), a small C# process using Beckhoff's official `TwinCAT.Ads` library. It talks to the local AMS router like any TwinCAT app, so no route or AMS TCP loopback is needed. One JSON request/response per line on stdin/stdout; the bridge converts raw PLC memory to JSON from the type information (64-bit integers as strings).
    - `AdsSymbolAccess` (`--driver ads-tcp`): pure TCP client (`ads-client`). Needs a static route or AMS TCP loopback, which the TwinCAT 4026 user-mode runtime does not provide out of the box.
    - `InMemoryPlc`: tests and the simulator.
  - The simulator is just an `InMemoryPlc` preset that changes values on every `step`, so it runs through real discovery.
  - PLC struct shapes live in `plc-contract.ts`. Their mapping to the neutral model is generic (`plc-mapping.ts`): it walks the protocol's zod schema and finds each field's PLC member by the naming convention (Hungarian prefix, array + count member, `bValid` entries, `bActive` for nullable structures, enums by index unless a table is registered). `components.ts` is the registry of component types (manifest value, PLC type, schemas). The PLC library `Syn_Visu` (library project `plc/Syn_Visu`, demo application `plc/Syn_Visu_Demo` on ADS port 852, exported releases in `plc/library/`, all in `plc/RPP_Visu.sln`) implements the contract described in `docs/plc-contract.md`; keep library, `plc-contract.ts` and doc in sync. PLC code is edited only through the TwinCAT MCP tools and follows `docs/plc-coding-guidelines.md` (company guideline; `Syn_Visu`'s contract names stay Beckhoff-style).
- `apps/web`: React + React Three Fiber.
  - **Seam:** `buildScene(config, snapshots, renderTime, hidden)` in `src/scene/scene-model.ts` is pure and builds one source's scene; `buildMachineScene(sources, hidden)` builds every source on its own timeline and puts them side by side (snap points and faults across sources, hidden components and sources, offline flag). It does hiding of user-hidden components, interpolation by `tRel`, latch + belt product positions, the product display lifecycle (normal / atTcp / placeholder / missed), Delta arms from the TCP (inverse kinematics), XTS gantry and loop movers (loop curves as semicircles) and products carried by movers, Cartesian robot parts and flange, gripper fingers and products carried by them, bodies of components drawn from their PLC description (detectors), faults (red parts, labels and the per-component fault list), zones with their allocation areas and CCS lines, origin shifts (shown origins, local measuring coordinates, belt coordinates), working areas and limit areas, the measure-mode snap points and component origins, and MCS → renderer conversion (`(x, y, z)mm → (x, z, −y)m`). Each component type is one kit in `KITS` (`build` through a shared context for zones, grippers, faults and carriers, optional `interpolate`), so `buildScene` itself knows no component type.
  - `SceneView.tsx` draws the model, one group per source (faded while the source is offline), and updates transforms per frame via refs. It also turns pointer gestures (mouse and touch) into selections and measuring points, with the decisions in `src/scene/picking.ts`. React re-renders only when the set of objects changes.
  - Look: every colour lives in `src/palette.ts` (status colours also reach the panels as CSS variables, set in `main.tsx`, so the 3D view, the tree and the timeline agree; chosen for red-green colour blindness). Lit machine parts are matte with fine edge lines and cast shadows; overlays (working, limit and box areas, zones, CCS lines, measuring and snap points, origins, axes) are unlit, not tone mapped and cast no shadow, so they keep their palette colour, and areas have a solid outline. The stage (`Stage` in `SceneView.tsx`): a generated studio environment (no download, works offline), a key light whose soft shadow covers the machine, a floor fading into the CSS background, the grid. Render quality (`src/scene/quality.ts`): auto / high / low per device; auto drops to low after 3 s below 45 fps and stays low; low means no shadows and resolution 1.
  - `src/product-history.ts` follows every product through the messages (entered the register, assigned, picked by which robot / mover / finger, placed, rejected, missed, left the register) for the inspector: live in `GatewayStore`, in playback from `Recording.products` up to the playback moment; both reach the inspector through `SceneFeed.productHistory`. It also logs countable product events (entered, picked by which robot, placed, rejected, missed; live the last 2 min) from which `metrics.ts` computes the figures of the last 60 s (picks/min per robot, products in/min, missed and rejected per conveyor, missed share), shown in the inspector; before a full minute of data the rates use the time covered.
  - `src/view-settings.ts` remembers per device (localStorage) how the 3D view was left: layers, hidden components and sources, camera, render quality; `parseViewSettings` falls back to the defaults entry by entry. Side panel state is remembered the same way in `App.tsx`.
  - `connection.ts` buffers snapshots per source and renders each source `RENDER_DELAY_MS` behind its newest one.
  - **Seam:** `src/recording.ts` (ADR 0006): `Recorder` stores every gateway message with its arrival time (unchanged products dropped, gzip blocks of 1 s, 10 min limit); `Recording.view(t)` gives every source at moment `t` as the machine scene takes it, plus `toFile` / `fromFile`; `Recording.events` are the timeline events found while recording (`timeline-events.ts`: a fault appears, a source goes offline or comes back, a product is missed, with the same rule as the scene, `isMissed`), marked on the timeline and reached by click or PageUp/PageDown; the playback clock (`tick`, `seek`, `step`, `playFrom`) is pure. `player.ts` plays a recording as a `SceneFeed`, the interface the 3D view and the inspector read live data through.
- Tests live only at the seams: gateway tests drive an `InMemoryPlc` (or several, combined) and assert on emitted messages; web tests call `buildScene`, `buildMachineScene`, the recording (any moment, config changes, product registers, timeline events, limit, file round trip) and the playback clock, `ProductHistory`, `metrics`, `parseViewSettings` and the render quality (`qualityFor`, `FrameRateSampler`), the inspector's generic state values and tables (`stateRows`); they also check the pointer picking in `src/scene/picking.ts` (tap or drag, nearest snap point on screen; mouse and touch tolerances). Small gateway seams for deployment are tested too: `resolveGatewayOptions` (flags, config file, default paths packaged vs. repo), `bridgeLaunch` (exe vs. dll), the bridge process (a node stand-in that dies: the request fails, the next one starts a new bridge) and `/health`. Rendering itself is not unit tested: the browser tests (`apps/web/e2e/`) drive the built app against the simulator through the main flows (scene and tree, side panels incl. reload, camera views, layers / hidden components / render quality / camera kept across a reload, measuring two points, record / play / seek / save / open, jumping to a fault on the timeline, a selected product's history and the metrics in the inspector) and check that the built app is split into parts of at most 800 KB (`manualChunks` in `apps/web/vite.config.ts`: three, react-three, react, vendor, app). The package is checked by a smoke run.

## TwinCAT MCP

- TwinCAT projects may be closed. If a call fails because no XAE is running (`find_projects` lists nothing, or RPC 0x800706BA), open the solution yourself: start `C:\Program Files\Beckhoff\TcXaeShell\Common7\IDE\TcXaeShell.exe "plc\RPP_Visu.sln"`, wait until the window title shows `RPP_Visu`, then call `initialize`.
- If a TwinCAT MCP call has not answered after 5 minutes, do not keep waiting. Retry it once (after `initialize` again). If it hangs again, try another way: a different tool for the same goal, smaller steps, or check whether XAE shows a modal dialog and ask the user to close it.
