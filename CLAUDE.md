# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language

Everything in this project is written in English: code, identifiers, comments, docs, ADRs, glossary, issues, PRs and commit messages. This applies even when the conversation with the user is in German.

## Commands

pnpm monorepo (pnpm 12 via corepack; prefix with `corepack` if `pnpm` is not on PATH).

- `pnpm install`
- `pnpm test`: all Vitest projects. Single file: `pnpm vitest run packages/machine-view/test/scene-model.test.ts`. Single test: add `-t "<name>"`.
- `pnpm typecheck`: `tsc` in every package
- `pnpm bench`: Vitest benchmarks in `apps/*/bench/` with 500 to 4800 products on one conveyor (gateway cycle, state JSON, receiving, product history, replay buffer, machine scene, scene frame); compare runs before and after a change, see `docs/performance.md`
- `pnpm test:e2e`: builds each web app and runs its browser tests in `apps/visualisation/e2e/` and `apps/configurator/e2e/` (Playwright, separate from `pnpm test`), one app after the other; the gateway runs with the simulator on :8090 (`E2E_PORT` to change it, e.g. when Windows reserves that port range) and serves the app's `dist`. On Windows it uses the installed Edge, elsewhere `E2E_CHANNEL=chromium` after `pnpm exec playwright install chromium`.
- `pnpm dev:gateway`: gateway with the simulator on :8080 (`-- --sim-products <n>` adds a buffer belt with n products for load tests)
- `pnpm dev:visualisation`, `pnpm dev:configurator`: a Vite dev server for one app that proxies `/ws` to the gateway (override with `GATEWAY_URL`); the configurator at `/configurator/`, as the gateway serves it
- `pnpm build`: builds `apps/visualisation/dist` and `apps/configurator/dist` (shared Vite settings in `scripts/web-app-build.mjs`). `pnpm build:bridge`: builds the .NET ADS bridge (`apps/ads-bridge`, needs the .NET 9 SDK).
- `pnpm start -- --driver ads --ams-net-id <id>` serves the built app plus the WebSocket on one port (`--help` lists the options; `--config <file>` reads them from JSON, flags win).
- `pnpm package`: builds the self-contained Windows package locally (for trying it out only; IPCs get the package of a GitHub release, made by the Release workflow on a `v*` tag, see `docs/releasing.md`), `dist/rpp-visualisation-<version>-win-x64.zip` (Windows, .NET SDK), with the newest compiled PLC libraries `plc/library/Syn_Visu_<version>.compiled-library` and `Syn_Config_<version>.compiled-library` (export it from XAE with "Save as compiled library" when releasing a library version). Deployment: `docs/deployment.md`, ADR 0004; install scripts in `deploy/windows/`.

## Architecture

A read-only web visualisation of packaging machines. It configures itself from what the PLC reports. Spec: GitHub issue #1.

- `packages/protocol`: the neutral data model (zod schemas plus types) shared by gateway and web, the Delta kinematics and the geometry of XTS tracks (`xts-track.ts`). All values are MCS: mm, degrees, Z up. A Delta reports only its TCP; the web derives the arms by inverse kinematics. XTS gantries (e.g. IDH) report their Z axis and per mover track position, X, C and gripper; XTS loops (e.g. Fxx) report per mover the position along the loop. Both describe their track as a chain of 250 mm XTS motor modules, straight or quarter curves, each with its own fault (ADR 0008). Cartesian robots report their X, Y, Z axes and gripper; their config says which axes they have (`axes`: `xyz`, `xz` without Y, a fixed beam; `xy` without Z, the flange at `zMin`; protocol version 17). Deltas, XTS gantries and Cartesian robots may have a limit area (box in the robot frame; protocol version 18 for the latter two; `_FB_VisuRobot.m_SetLimitArea` sets it through `m_LimitArea`, the web draws it through the kit context's `addLimitArea`) and a TCP limit area (`tcpLimitArea`, protocol version 19: a box around the TCP, on an XTS gantry around every mover's flange, relative to it along the robot frame's axes; `_FB_VisuRobot.m_SetTcpLimitArea`); every zone may have an allocation offset. Every kinematics may define gripper fingers (cylinders) whose poses the PLC reports absolute in the MCS; tool rotations exist only through them, and a picked product hangs at its `fingerId`. Every finger has an offset on the gripper flange (protocol version 20, ADR 0018): while its state reports no pose (`poseReported` false), the scene places it there, on the flange frame its kit computes (`addGripper`; Syn_Visu `m_SetFingerOffset`, `m_SetFingersOnFlange` for XTS). Every component, every XTS mover and every track module may report a fault with a message. Every zone has a CCS offset (the robot's conveyor coordinate system on that belt) and every component an origin shift: where its coordinate system lies relative to its pose; a conveyor's belt coordinates count from it. Product types are boxes, cylinders (two diameters: round or oval) or rounded boxes. Zones belong to robots, detectors and stations alike and have no kind; a zone spans its belt's width or only a lane of it (`startY`/`endY` in the conveyor's coordinate system, may reach past the belt's sides; protocol version 15); a zone end or CCS past the belt start or end gives a warning, a CCS outside its zone does not. A conveyor may have no body (`body`, protocol version 16): then only its products, zones and axis (ball at its shifted origin, line, direction arrow) are drawn. Detectors (vision system, product sensor) and stations (reject unit, labeller, ...) are drawn only from the bodies their PLC function block describes (box, cylinder, frustum with a role), so the web needs no code per type (ADR 0007). A product names its client, the component that changed it last (robot, detector, station), and its state before that change (`lastClientId`, `previousState`; protocol version 13, ADR 0009); the product history and the metrics are counted per client from these. Track modules came with protocol version 12. A product may carry a product mark (`mark` 1 to 4, 0 = none; protocol version 21), which the PLC sets to single it out (`m_SetProductMark`) and names once per source in the manifest (`aMarkNames` → the config's `marks`); a marked product is drawn in its mark's colour (`MARK` in the palette) instead of its state colour while the layer "Product marks" is on, only the selection wins over it (`productMark`, `markName` in `machine-facts.ts`; marked products form their own product groups). A product's latch pose is given in its conveyor's coordinate system (pose + origin shift, X along the belt; protocol version 14, ADR 0010), from which the belt travel moves it. Adding a component type: `docs/adding-a-component.md`.
- `apps/gateway`: Node + TypeScript, run with tsx.
  - `createGateway` reads one PLC source (AmsNetId + ADS port): discovery (manifest at `GVL_Visu.stManifest` → protocol version check → type check per entry → read `stConfig`) and cyclic sum-reads of every `stState` together with `nConfigVersion`. It emits `status` / `config` / `state` messages, each with its `sourceId`, and waits `RECONNECT_MS` after a failure. The server fans them out over the WebSocket and answers `GET /health` (per source connected / last error / time of the last state, plus `acquisition`: read and map times, state message size, products and register anomalies from `acquisition-stats.ts`; 200 or 503) from them (`health.ts`). The server turns every message into JSON once for all browsers; a client connecting with `/ws?changes=1` (the web app does) gets states in register form, per conveyor only the changed products plus `registers` (the id order), from one shared `RegisterEncoder` (ADR 0013), and every product again after connecting or a dropped state. It also serves the PLC library guide for PLC programmers at `/docs` (ADR 0014, `docs-page.ts`), built in memory on the first request from `docs/plc-library-guide.md` with its diagrams (`docs/images/*.svg`, inlined with ids prefixed per file); `/docs/schema.json` is the JSON Schema of the messages, generated from the protocol's zod schemas (every field has a `.describe()` text; a test fails without one; ADR 0012). Guide and diagrams come from `docs/` (embedded by `pnpm package`, `docs-texts.ts`); `docs/api.md` documents the WebSocket for client programmers in the repo only. The `/health` report and the recording file lines are zod schemas in `@rpp/protocol` too. Several sources (other IPCs over ADS routes, ADR 0005) each get their own gateway and loop; `combineGateways` merges their messages for the server. Manifest ids are unique only per source.
  - **Seam:** `SymbolAccess` (read / typeOf / sumRead). `sumRead(paths, { changes })` may give a product register as changes (`ChangedEntries`: `$ids` in order, `$changed` entries; ADR 0013) within a session the gateway starts on every discovery; the mapping (`plc-mapping.ts`, `EntryMemory`) maps only those and keeps the other product objects, and an unknown id makes the gateway start a new session and read again. Adapters:
    - `AdsBridgeSymbolAccess` (`--driver ads`, default for real PLCs): spawns `apps/ads-bridge` (the self-contained `AdsBridge.exe` when packaged, else the dll through `dotnet`; see `bridgeLaunch`), a small C# process using Beckhoff's official `TwinCAT.Ads` library. It talks to the local AMS router like any TwinCAT app, so no route or AMS TCP loopback is needed. One JSON request/response per line on stdin/stdout; the bridge converts raw PLC memory to JSON from the type information (64-bit integers as strings). Of a large array with a count member (a product register) it reads only the counted entries plus a reserve (`ReadPlan.cs`), so a register's array size costs no ADS bandwidth; asked for changes, it compares each entry's bytes by `nId` with the previous read and converts only the changed ones.
    - `AdsSymbolAccess` (`--driver ads-tcp`): pure TCP client (`ads-client`). Needs a static route or AMS TCP loopback, which the TwinCAT 4026 user-mode runtime does not provide out of the box.
    - `InMemoryPlc`: tests and the simulator; gives registers as changes like the bridge.
  - The simulator is just an `InMemoryPlc` preset that changes values on every `step`, so it runs through real discovery.
  - **Parameter sets** (ADR 0017): a PLC whose application uses the library `Syn_Config` lists its parameter FBs in `GVL_Config.stManifest` (`config-contract.ts`; own protocol version `CONFIG_PROTOCOL_VERSION`). `parameter-access.ts` finds them during discovery, reads each one's `stStatus` and `stActive` in the cyclic sum-read (with a register memory like the states) and publishes a `parameters` message per source when it changes (only for a PLC with Syn_Config; `writable` only with `--allow-write`, option `allowWrite`). The server takes the WebSocket commands `writeParameters` / `resetParameters` (`ClientMessageSchema`) and answers `writeResult` to that client; the gateway refuses a command on another active version than its `baseVersion` and writes the set through `SymbolAccess.sumWrite` (leaf paths from the protocol schema by the naming convention, `plc-writing.ts`; indices from 0, the ADS bridge maps them to the PLC's lower bound and writes them in one ADS sum-write, `SumWrite.cs`; the `ads-tcp` driver cannot write), `bStaged` or `bReset` last. The PLC side is the library `Syn_Config` (`plc/Syn_Config`, contract and usage in `docs/config-contract.md`; a parameter FB per component type, `vision` / `sensor` / `station` sharing one structure; the demo wires Infeed 1, Delta 1 and Vision 1 in `P_VisuDemoDelta` and the IDH in `P_VisuDemoIdh`). Every component type has a parameter set (`PARAMETER_FIELDS`: pose, origin shift and its zones, product types, track modules, gripper fingers with their offsets, working and limit areas; never hardware; config protocol version 2 since the fingers, Syn_Config 2.0). `config-emulation.ts` emulates Syn_Config and an application passing its effective values on to Syn_Visu, generically by the naming convention (`plcMembers` in `plc-writing.ts`), for the simulator (one component of every type) and the tests. The protocol side is `packages/protocol/src/parameters.ts` (`ServerMessageSchema` is everything the gateway sends).
  - PLC struct shapes live in `plc-contract.ts`. Their mapping to the neutral model is generic (`plc-mapping.ts`): it walks the protocol's zod schema and finds each field's PLC member by the naming convention (Hungarian prefix, array + count member, `bValid` entries, `bActive` for nullable structures, enums by index unless a table is registered). `components.ts` is the registry of component types (manifest value, PLC type); their schemas come from `COMPONENT_SCHEMAS` in `@rpp/protocol`, the one list of component types from which the config and state unions follow. The PLC library `Syn_Visu` (library project `plc/Syn_Visu`, demo application `plc/Syn_Visu_Demo` on ADS port 852, exported releases in `plc/library/`, all in `plc/RPP_Visu.sln`) implements the contract described in `docs/plc-contract.md`; keep library, `plc-contract.ts` and doc in sync (and the usage guide for PLC programmers with its method reference and diagrams, `docs/plc-library-guide.md`, served at `/docs`). PLC code is edited only through the TwinCAT MCP tools and follows `docs/plc-coding-guidelines.md` (company guideline; `Syn_Visu`'s contract names stay Beckhoff-style).
- The web: two apps and the library they share (ADR 0019), React + React Three Fiber. Each app imports the library only through its entry point `@rpp/machine-view` (`src/index.ts`; its `package.json` `exports` allow no deeper import, except the palette for the gateway's docs page and `styles.css`), and neither app imports the other.
- `packages/machine-view`: the machine view, everything both apps show the machine with. It knows neither app.
  - **Seam:** `buildScene(config, snapshots, renderTime, hidden)` in `src/scene/scene-model.ts` is pure and builds one source's scene; `buildMachineScene(sources, hidden)` builds every source on its own timeline and puts them side by side (snap points and faults across sources, hidden components and sources, offline flag). It does hiding of user-hidden components, interpolation by `tRel`, latch + belt product positions, the product display lifecycle (normal / atTcp / placeholder / missed), Delta arms from the TCP (inverse kinematics; the TCP triad and flange frame keep the MCS axes), XTS gantry and loop tracks laid out from their modules (curve modules as quarter circles) with module faults, their movers and products carried by movers, Cartesian robot parts and flange, gripper fingers and products carried by them, bodies of components drawn from their PLC description (detectors, stations; an active body lights up), faults (red parts, labels and the per-component fault list), zones with their allocation areas and CCS lines, origin shifts (shown origins, local measuring coordinates, belt coordinates), working areas and limit areas, TCP limit areas with their limit violations (both boxes red, the violation in the fault list under `limitViolations` and as a label; not checked while the source is offline; ADR 0015), the measure-mode snap points and component origins, and MCS → renderer conversion (`(x, y, z)mm → (x, z, −y)m`). Each component type is one kit in its own module in `src/scene/kits/` (e.g. `delta.ts`; the XTS gantry and loop share `xts-track.ts`, body components `bodies.ts`), registered in `KITS` (`build` through a shared context for zones, grippers, faults and carriers, optional `interpolate`; the kit vocabulary is `kits/kit.ts`), so `buildScene` itself knows no component type. Its meshes live in its module in `src/scene/views/` (e.g. `delta.tsx`; XTS gantry and loop share `xts.tsx`; shared mesh helpers in `common.tsx`). Every kind of part is one entry in `SCENE_PARTS` (its owner, for hiding, and what of it changes the drawn objects), from which the empty scene, hiding and the structural signature (`sceneStructure`) follow; `PART_VIEWS` in `SceneView.tsx` draws each kind. Both are typed over `SceneModel`, so a new kind cannot be forgotten in either.
  - `SceneView.tsx` draws the model from one function giving the scene sources of a moment (the live machine, a recording in playback, a draft), one group per source (faded while the source is offline), and updates transforms per frame via refs. Products on a belt (normal, missed) are drawn per solid as one `InstancedMesh` with colours per instance and their edge lines as one instanced line set sharing its matrices (`ProductInstances`; which products share a mesh and its capacity, which only grows, is decided in `src/scene/product-groups.ts`); placeholders and carried products stay single meshes. Every component's coordinate system (an origin triad where its origin shift puts it) is drawn on the layer `origins` ("Coordinate systems": off by default in the visualisation, on in the configurator; both apps show the same layer toggles, `LayerToggles`) and always in measure mode; the triads follow the scene of every frame, so they move with a dragged component. Product snap points and the corners of TCP limit areas are built only in measure mode (`buildMachineScene(..., { measureSnapPoints })`). It also turns pointer gestures (mouse and touch) into selections and measuring points, with the decisions in `src/scene/picking.ts`: a `PressTracker` (one per gesture: selecting, measuring) tells which presses are taps (not a drag, a pinch or a cancelled touch; in measure mode a finger may slide), and `pickOnScreen` finds the snap point under the pointer through a projection. React re-renders only when the set of objects changes: `src/scene/scene-frame.ts` (pure) takes each frame's scene, per source a `SourceFrame` (whether the structure changed, from `sceneStructure` and the product groups; parts by key, `part(kind, key)`, for the meshes' per-frame updates; the products by group) and for the machine a `MachineFrame` (sources online, snap points, origins; whether faults changed).
  - Look: every colour lives in `src/palette.ts` (status colours also reach the panels as CSS variables, set in each app's `main.tsx`, so the 3D view, the tree and the timeline agree; chosen for red-green colour blindness). Lit machine parts are matte with fine edge lines; overlays (working, limit and box areas, zones, CCS lines, measuring and snap points, origins, axes) are unlit and not tone mapped, so they keep their palette colour, and areas have a solid outline. The stage (`Stage` in `SceneView.tsx`): a generated studio environment (no download, works offline), a key light from nearly above, a floor fading into the CSS background, the grid. One fixed render quality for weak panel PCs: no shadows, resolution 1 (`DPR` in `SceneView.tsx`). The shared look is `src/styles.css`; each app adds its own stylesheet after it.
  - `src/naming.ts` names fields, list entries and components for both apps (`fieldLabel`, `singular`, `componentName`). `src/machine-facts.ts` holds the rules the scene, the timeline, the product history, the metrics and the inspector share: how a fault reads (`faultText`), where a product is on its belt and when it is missed (`productBeltX`, `isMissed`), a zone's sides and what is wrong with it on its belt (`zoneSides`, `zoneWarnings`, `onBelt`; the configurator's problems use them too), what a component is called (`componentName`), where the TCP limit areas are and which limit violations there are (`tcpLimitBoxes`, `limitViolations`: a TCP limit area overlapping another robot's limit area or another TCP limit area, or leaving its own robot's; each box prepared once with `orient`, then `orientedOverlap` in `src/scene/frames.ts`: a sphere test first, the separating axis test only for boxes that come close; no checks at all without TCP limit areas).
  - `src/gateway-connection.ts`: `GatewayConnection`, the WebSocket both apps read the gateway through, reconnects, hands every message on parameter sets to `onParameterMessage`, restores states from register form (`RegisterDecoder` in `@rpp/protocol`, `src/registers.ts` there; ADR 0013; recordings store the same form; an unchanged product stays the same object, which the product history and the encoder use to skip it, so never mutate a product) and folds every message into `Sources`.
  - **Seam:** `src/sources.ts`: `Sources` is what the web app knows about every source at one moment, live and in playback alike: name, status and config, the states of the current config version (a new config version or a restarting `tRel` starts a new timeline; the last second, at least two states), the render time `RENDER_DELAY_MS` behind the newest state on the source's own `tRel` axis, and `online`. It has no clock: every time is given (`apply(at, message)`, `sceneSources(t)`). `GatewayConnection` keeps one on the `performance.now()` axis, the `Recorder` one for the context of its blocks, and `Recording.view(t)` builds a fresh one from the blocks. When the browser loses the gateway, `gatewayLost()` gives a `status` per source (`lastError` `GATEWAY_LOST`) that `GatewayConnection` applies and hands to its listeners like the gateway's own, so recordings and the replay buffer show the outage.
- `apps/visualisation`: the visualisation, served at `/`.
  - `src/product-history.ts` follows every product through the messages (entered the register, assigned, picked, placed, released or rejected and by which client, mover and finger, marked, re-marked or unmarked, missed, left the register) for the inspector: live in `LiveMachine` (`src/live-machine.ts`, built on the connection), in playback from `Recording.products` up to the playback moment; both reach the inspector through `SceneFeed.productHistory`. It also logs countable product events (entered, picked, placed, rejected, missed, each with its client; live the last 2 min) from which `metrics.ts` computes the figures of the last 60 s (per client what it detected, picked, placed and rejected per minute, products in/min, missed and rejected per conveyor, missed share), shown in the inspector; before a full minute of data the rates use the time covered.
  - `src/view-settings.ts` remembers per device (localStorage) how the 3D view was left: layers, hidden components and sources, camera; `parseViewSettings` falls back to the defaults entry by entry. Both apps have the same side panels, opened and closed by a tab on the 3D view's edge and resized by dragging it, each remembered per device (`useSidePanel`, `SidePanelControls` in `@rpp/machine-view`).
  - **Seam:** `src/recording.ts` (ADR 0006): `Recorder` stores every gateway message with its arrival time (unchanged products dropped, gzip blocks of 1 s, 10 min limit); `Recording.view(t)` gives every source at moment `t` as the machine scene takes it, plus `toFile` / `fromFile`; `Recording.events` are the timeline events found while recording (`timeline-events.ts`: a fault appears, a source goes offline or comes back, a product is missed, a limit violation starts, with the same rules as the scene, `isMissed`, `limitViolations`), marked on the timeline and reached by click or PageUp/PageDown; the playback clock (`tick`, `seek`, `step`, `playFrom`) is pure. The replay buffer (ADR 0011) is a `Recorder` in replay-buffer mode (`Recorder.replayBuffer()`, `windowMs` = `REPLAY_BUFFER_MS`, 60 s before its newest message, whole blocks dropped), kept by the viewer and fed every message from page load; `snapshot()` gives the kept blocks as an ordinary recording starting at 0 (events, products and snapshot times found again from the blocks), behind the icon button right of Record. `player.ts` plays a recording as a `SceneFeed`; its clock moves on with `frame(now)`, which the 3D view calls once per drawn frame.
  - **Seam:** `src/viewer.ts`: the `Viewer` is what the user is looking at, live or a recording in playback, and the `SceneFeed` the 3D view and the inspector read (`SceneFeed`, `src/viewer.ts`; it hands on to the `LiveMachine` or the `Player`). It holds the mode, the shown sources, the replay buffer, the live recording with its 10 min limit, the shown recording and whether it is saved, and the commands (record, stop, replay, open, save, discard, live / playback; one recording at a time, an unsaved one is discarded only after `confirmDiscard`). It reads the live machine through `LiveFeed` (`LiveMachine`, a fake in tests). `RecordingControls.tsx` only binds it to the page (`useRecordingControls`: the recording bar, files, downloads, the warning before closing).
- `apps/configurator`: the configurator, served at `/configurator/` (built with that base path).
  - **Seam:** the configurator (ADR 0016). It edits a draft (`DraftSchema` in `@rpp/protocol`: every component's `ComponentConfig` with source and manifest id, saved as `<name>.rpp-draft.json`). `Configurator` holds the draft, the selection, undo and redo (a drag between `beginGesture` / `endGesture` is one step), the draft file (save, open, new; unsaved changes are discarded only after `confirmDiscard`) and the problems (counted in the status bar and listed above it on a click, as the visualisation lists its discovery errors; a click on one selects its component; `validateDraft`: errors such as an id used twice or a zone on a conveyor neither the draft nor its connected PLC has, the zone warnings of `zoneWarnings` in `machine-facts.ts`); every change is an edit applied by the pure `applyEdit` (`edits.ts`; a path may name list entries by index, e.g. `["zones", "1", "end"]`). Zones are added on a conveyor of the same source (`addZone`, the middle 500 mm) and dragged edge by edge (`dragZone`: start, end, CCS, sides; an MCS point turned into belt coordinates by `belt-coordinates.ts`); product types are added per conveyor (`addProductType`), track modules to an XTS track (`addModule`, 250 mm of a kind), bodies to a detector or station (`addBody`), a limit area or TCP limit area to a robot (`addArea` starting as `defaultArea`: the robot's reach, a box around the flange; `removeArea`); list entries are removed with `removeListEntry`. An XTS loop whose track does not end where it starts is a warning, a module without a length or a track without modules an error. A robot's gripper is laid out in a top view of its flange (`FingerLayout.tsx`; `addFinger`, `moveFinger` on a 5 mm grid, one undo step per drag; a finger without a diameter or height is an error), and a draft robot with fingers is drawn at rest (`rest-states.ts`), its fingers placed by their offsets (ADR 0018). `frame()` gives the draft as `SceneSource`s whose only states are a preview product of each product type on its belt and the rest states of robots with fingers, so `SceneView` draws it with the visualisation's kits. The palette (`component-defaults.ts`: every component type; assumed hardware geometry) places by a click (middle of the view) or a drop (under the pointer at the type's height), on a 10 mm grid. The property panel reads a component's fields from its config schema (`property-fields.ts`: values, nested objects, every list entry as a group (zones, product types, track modules with their kind as a choice, bodies, fingers); optional areas as a group while present, else named in `optionals`; a zone's conveyor is chosen from the source's conveyors). `EditControls.tsx`, drawn inside `SceneView` (its `children`), holds the handles (move handle: drags the selected component over the floor, caught by other components' snap points; zone handles) and the floor picker for drops. The camera views (`ViewControls.tsx`) are shared with the visualisation and frame the parts where they are now (conveyors, Delta bases and effectors, every component's origin). Online (`ConfiguratorLive`: `GatewayLive` in `src/gateway-live.ts`, built on the connection, a fake in tests; `start` / `stop`) it imports a source (`importSource`, one undo step) or a component only the PLC has (`importComponent`), reconciles the draft with the PLCs (`reconciliation.ts`: per component matched / changed / draftOnly / typeMismatch / noPlc, plus `plcOnly`), draws the live states of matched components over the draft and the PLC's version of changed ones as a ghost (`ghostSourceId`, a source that is never online, so it is drawn faded), and hints where the draft assumed other hardware than its PLC has (`HARDWARE_FIELDS` in `component-defaults.ts`, `hardwareHints`; `adoptPlcHardware` takes the PLC's). Writing (`writing.ts`; `GatewayLive` sends commands and keeps the `parameters` per source): `writePlan(sourceId)` lists the parameter values a write changes (`leafChanges` against the active set) or why the source is blocked (no Syn_Config, no `--allow-write`, errors in the draft); `write(sourceId)` stages every changed component on its active version, and `writes` follows each until its PLC handled it (staged, waiting, applied, rejected, failed); `resetParameters` returns a component to its program values; `wiringHints` warns where the visualisation shows other values than the active set, `unwritableHints` of a changed component its PLC has no parameter set for (the write plan names it, `unwritable`).
- Tests live only at the seams: gateway tests drive an `InMemoryPlc` (or several, combined) and assert on emitted messages; web tests call `buildScene`, `buildMachineScene`, `Sources`, the `Viewer` (record, limit, replace, replay, open, save, live), the recording (any moment, config changes, product registers, timeline events, limit, file round trip), the replay buffer's snapshot and the playback clock, `ProductHistory`, `metrics`, `parseViewSettings`, the inspector's generic state values and tables (`stateRows`); they also check the pointer picking in `src/scene/picking.ts` (tap or drag, pinch, cancelled touch, sliding finger, nearest snap point on screen; mouse and touch tolerances) the product groups in `src/scene/product-groups.ts`, the scene frame (`scene-frame.ts`: when the view re-renders, parts by key) and the `Configurator` (place on the grid, set values, move and turn, undo / redo and gestures, remove, id and source changes, problems, draft file save / open / new; every palette type, track modules, bodies and optional areas with their property fields, `configurator-types.test.ts`; the gripper layout, `configurator-fingers.test.ts`). The docs page is tested at the gateway seam (`docs-page.test.ts`: every diagram the guide links inlined with unique ids, every in-page link resolves, every schema field described, simulator messages valid against the JSON Schema, `/docs` served with and without a web app); `web-pages.test.ts` checks that the visualisation is served at `/` and the configurator from its own build at `/configurator/`. Small gateway seams for deployment are tested too: `resolveGatewayOptions` (flags, config file, default paths packaged vs. repo), `bridgeLaunch` (exe vs. dll), the bridge process (a node stand-in that dies: the request fails, the next one starts a new bridge) and `/health`. Rendering itself is not unit tested: the browser tests (`e2e/` of each app) drive the built apps against the simulator through the main flows (scene and tree, side panels incl. reload, a limit violation of the simulator in the tree and on the replayed timeline, camera views, layers / hidden components / camera kept across a reload, measuring two points, record / play / seek / save / open, replaying the last minute, jumping to a fault on the timeline, a selected product's history and the metrics in the inspector, a product the simulator marked found by its mark's colour in the replay and named in the inspector until the layer "Product marks" is off, the PLC guide link opening `/docs` with its diagrams and without broken anchors; in the configurator placing, editing, undo, saving and opening a draft, editing an XTS loop's modules, a station's bodies and a limit area, and writing to the simulator a Delta's zone and an XTS gantry's track, laying out a Delta's fingers in the flange's top view, closing and resizing its side panels) and check that the built app is split into parts of at most 800 KB (`manualChunks` in `scripts/web-app-build.mjs`: three, react-three, react, vendor, app). The package is checked by a smoke run.
