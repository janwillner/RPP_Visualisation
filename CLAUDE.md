# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Language

Everything in this project is written in English: code, identifiers, comments, docs, ADRs, glossary, issues, PRs and commit messages. This applies even when the conversation with the user is in German.

## Commands

pnpm monorepo (pnpm 12 via corepack; prefix with `corepack` if `pnpm` is not on PATH).

- `pnpm install`
- `pnpm test`: all Vitest projects. Single file: `pnpm vitest run apps/web/test/scene-model.test.ts`. Single test: add `-t "<name>"`.
- `pnpm typecheck`: `tsc` in every package
- `pnpm bench`: Vitest benchmarks in `apps/*/bench/` with 500 to 4800 products on one conveyor (gateway cycle, state JSON, receiving, product history, replay buffer, machine scene); compare runs before and after a change, see `docs/performance.md`
- `pnpm test:e2e`: builds the web app and runs the browser tests in `apps/web/e2e/` (Playwright, separate from `pnpm test`); the gateway runs with the simulator on :8090 (`E2E_PORT` to change it, e.g. when Windows reserves that port range) and serves `dist`. On Windows it uses the installed Edge, elsewhere `E2E_CHANNEL=chromium` after `pnpm exec playwright install chromium`.
- `pnpm dev:gateway`: gateway with the simulator on :8080 (`-- --sim-products <n>` adds a buffer belt with n products for load tests)
- `pnpm dev:web`: Vite dev server that proxies `/ws` to the gateway (override with `GATEWAY_URL`)
- `pnpm build`: builds `apps/web/dist`. `pnpm build:bridge`: builds the .NET ADS bridge (`apps/ads-bridge`, needs the .NET 9 SDK).
- `pnpm start -- --driver ads --ams-net-id <id>` serves the built app plus the WebSocket on one port (`--help` lists the options; `--config <file>` reads them from JSON, flags win).
- `pnpm package`: builds the self-contained Windows package for IPCs, `dist/rpp-visualisation-<version>-win-x64.zip` (Windows, .NET SDK), with the newest compiled PLC library `plc/library/Syn_Visu_<version>.compiled-library` (export it from XAE with "Save as compiled library" when releasing a library version). Deployment: `docs/deployment.md`, ADR 0004; install scripts in `deploy/windows/`.

## Architecture

A read-only web visualisation of packaging machines. It configures itself from what the PLC reports. Spec: GitHub issue #1.

- `packages/protocol`: the neutral data model (zod schemas plus types) shared by gateway and web, the Delta kinematics and the geometry of XTS tracks (`xts-track.ts`). All values are MCS: mm, degrees, Z up. A Delta reports only its TCP; the web derives the arms by inverse kinematics. XTS gantries (e.g. IDH) report their Z axis and per mover track position, X, C and gripper; XTS loops (e.g. Fxx) report per mover the position along the loop. Both describe their track as a chain of 250 mm XTS motor modules, straight or quarter curves, each with its own fault (ADR 0008). Cartesian robots report their X, Y, Z axes and gripper. Deltas may have a limit area (box in the robot frame); every zone may have an allocation offset. Every kinematics may define gripper fingers (cylinders) whose poses the PLC reports absolute in the MCS; tool rotations exist only through them, and a picked product hangs at its `fingerId`. Every component, every XTS mover and every track module may report a fault with a message. Every zone has a CCS offset (the robot's conveyor coordinate system on that belt) and every component an origin shift: where its coordinate system lies relative to its pose; a conveyor's belt coordinates count from it. Product types are boxes, cylinders (two diameters: round or oval) or rounded boxes. Zones belong to robots, detectors and stations alike and have no kind. Detectors (vision system, product sensor) and stations (reject unit, labeller, ...) are drawn only from the bodies their PLC function block describes (box, cylinder, frustum with a role), so the web needs no code per type (ADR 0007). A product names its client, the component that changed it last (robot, detector, station), and its state before that change (`lastClientId`, `previousState`; protocol version 13, ADR 0009); the product history and the metrics are counted per client from these. Track modules came with protocol version 12. A product's latch pose is given in its conveyor's coordinate system (pose + origin shift, X along the belt; protocol version 14, ADR 0010), from which the belt travel moves it. Adding a component type: `docs/adding-a-component.md`.
- `apps/gateway`: Node + TypeScript, run with tsx.
  - `createGateway` reads one PLC source (AmsNetId + ADS port): discovery (manifest at `GVL_Visu.stManifest` → protocol version check → type check per entry → read `stConfig`) and cyclic sum-reads of every `stState` together with `nConfigVersion`. It emits `status` / `config` / `state` messages, each with its `sourceId`, and waits `RECONNECT_MS` after a failure. The server fans them out over the WebSocket and answers `GET /health` (per source connected / last error / time of the last state, plus `acquisition`: read and map times, state message size, products and register anomalies from `acquisition-stats.ts`; 200 or 503) from them (`health.ts`). The server turns every message into JSON once for all browsers; a client connecting with `/ws?changes=1` (the web app does) gets states in register form, per conveyor only the changed products plus `registers` (the id order), from one shared `RegisterEncoder` (ADR 0013), and every product again after connecting or a dropped state. It also serves the API documentation (ADR 0012, `api-docs.ts`) at `/docs`, built in memory on the first request: the introduction `docs/api.md`, a reference generated from the protocol's zod schemas (every field has a `.describe()` text; a test fails without one) with simulator messages as examples, the server options (`OPTION_HELP`, shared with `--help`), the PLC contract and the library guide; `/docs/schema.json` is the JSON Schema. The Markdown comes from `docs/` (embedded by `pnpm package`, `docs-texts.ts`). The `/health` report and the recording file lines are zod schemas in `@rpp/protocol` too. Several sources (other IPCs over ADS routes, ADR 0005) each get their own gateway and loop; `combineGateways` merges their messages for the server. Manifest ids are unique only per source.
  - **Seam:** `SymbolAccess` (read / typeOf / sumRead). `sumRead(paths, { changes })` may give a product register as changes (`ChangedEntries`: `$ids` in order, `$changed` entries; ADR 0013) within a session the gateway starts on every discovery; the mapping (`plc-mapping.ts`, `EntryMemory`) maps only those and keeps the other product objects, and an unknown id makes the gateway start a new session and read again. Adapters:
    - `AdsBridgeSymbolAccess` (`--driver ads`, default for real PLCs): spawns `apps/ads-bridge` (the self-contained `AdsBridge.exe` when packaged, else the dll through `dotnet`; see `bridgeLaunch`), a small C# process using Beckhoff's official `TwinCAT.Ads` library. It talks to the local AMS router like any TwinCAT app, so no route or AMS TCP loopback is needed. One JSON request/response per line on stdin/stdout; the bridge converts raw PLC memory to JSON from the type information (64-bit integers as strings). Of a large array with a count member (a product register) it reads only the counted entries plus a reserve (`ReadPlan.cs`), so a register's array size costs no ADS bandwidth; asked for changes, it compares each entry's bytes by `nId` with the previous read and converts only the changed ones.
    - `AdsSymbolAccess` (`--driver ads-tcp`): pure TCP client (`ads-client`). Needs a static route or AMS TCP loopback, which the TwinCAT 4026 user-mode runtime does not provide out of the box.
    - `InMemoryPlc`: tests and the simulator; gives registers as changes like the bridge.
  - The simulator is just an `InMemoryPlc` preset that changes values on every `step`, so it runs through real discovery.
  - PLC struct shapes live in `plc-contract.ts`. Their mapping to the neutral model is generic (`plc-mapping.ts`): it walks the protocol's zod schema and finds each field's PLC member by the naming convention (Hungarian prefix, array + count member, `bValid` entries, `bActive` for nullable structures, enums by index unless a table is registered). `components.ts` is the registry of component types (manifest value, PLC type, schemas). The PLC library `Syn_Visu` (library project `plc/Syn_Visu`, demo application `plc/Syn_Visu_Demo` on ADS port 852, exported releases in `plc/library/`, all in `plc/RPP_Visu.sln`) implements the contract described in `docs/plc-contract.md`; keep library, `plc-contract.ts` and doc in sync (and the usage guide for PLC programmers, `docs/plc-library-guide.md`). PLC code is edited only through the TwinCAT MCP tools and follows `docs/plc-coding-guidelines.md` (company guideline; `Syn_Visu`'s contract names stay Beckhoff-style).
- `apps/web`: React + React Three Fiber.
  - **Seam:** `buildScene(config, snapshots, renderTime, hidden)` in `src/scene/scene-model.ts` is pure and builds one source's scene; `buildMachineScene(sources, hidden)` builds every source on its own timeline and puts them side by side (snap points and faults across sources, hidden components and sources, offline flag). It does hiding of user-hidden components, interpolation by `tRel`, latch + belt product positions, the product display lifecycle (normal / atTcp / placeholder / missed), Delta arms from the TCP (inverse kinematics; the TCP triad and flange frame keep the MCS axes), XTS gantry and loop tracks laid out from their modules (curve modules as quarter circles) with module faults, their movers and products carried by movers, Cartesian robot parts and flange, gripper fingers and products carried by them, bodies of components drawn from their PLC description (detectors, stations; an active body lights up), faults (red parts, labels and the per-component fault list), zones with their allocation areas and CCS lines, origin shifts (shown origins, local measuring coordinates, belt coordinates), working areas and limit areas, the measure-mode snap points and component origins, and MCS → renderer conversion (`(x, y, z)mm → (x, z, −y)m`). Each component type is one kit in `KITS` (`build` through a shared context for zones, grippers, faults and carriers, optional `interpolate`), so `buildScene` itself knows no component type.
  - `SceneView.tsx` draws the model, one group per source (faded while the source is offline), and updates transforms per frame via refs. Products on a belt (normal, missed) are drawn per solid as one `InstancedMesh` with colours per instance and their edge lines as one instanced line set sharing its matrices (`ProductInstances`); placeholders and carried products stay single meshes. Product snap points are built only in measure mode (`buildMachineScene(..., { productSnapPoints })`). It also turns pointer gestures (mouse and touch) into selections and measuring points, with the decisions in `src/scene/picking.ts`. React re-renders only when the set of objects changes.
  - Look: every colour lives in `src/palette.ts` (status colours also reach the panels as CSS variables, set in `main.tsx`, so the 3D view, the tree and the timeline agree; chosen for red-green colour blindness). Lit machine parts are matte with fine edge lines; overlays (working, limit and box areas, zones, CCS lines, measuring and snap points, origins, axes) are unlit and not tone mapped, so they keep their palette colour, and areas have a solid outline. The stage (`Stage` in `SceneView.tsx`): a generated studio environment (no download, works offline), a key light from nearly above, a floor fading into the CSS background, the grid. One fixed render quality for weak panel PCs: no shadows, resolution 1 (`DPR` in `SceneView.tsx`).
  - `src/product-history.ts` follows every product through the messages (entered the register, assigned, picked, placed, released or rejected and by which client, mover and finger, missed, left the register) for the inspector: live in `GatewayStore`, in playback from `Recording.products` up to the playback moment; both reach the inspector through `SceneFeed.productHistory`. It also logs countable product events (entered, picked, placed, rejected, missed, each with its client; live the last 2 min) from which `metrics.ts` computes the figures of the last 60 s (per client what it detected, picked, placed and rejected per minute, products in/min, missed and rejected per conveyor, missed share), shown in the inspector; before a full minute of data the rates use the time covered.
  - `src/view-settings.ts` remembers per device (localStorage) how the 3D view was left: layers, hidden components and sources, camera; `parseViewSettings` falls back to the defaults entry by entry. Side panel state is remembered the same way in `App.tsx`.
  - `connection.ts` restores states from register form (`RegisterDecoder` in `@rpp/protocol`, `src/registers.ts` there; ADR 0013; recordings store the same form; an unchanged product stays the same object, which the product history and the encoder use to skip it, so never mutate a product), buffers snapshots per source and renders each source `RENDER_DELAY_MS` behind its newest one.
  - **Seam:** `src/recording.ts` (ADR 0006): `Recorder` stores every gateway message with its arrival time (unchanged products dropped, gzip blocks of 1 s, 10 min limit); `Recording.view(t)` gives every source at moment `t` as the machine scene takes it, plus `toFile` / `fromFile`; `Recording.events` are the timeline events found while recording (`timeline-events.ts`: a fault appears, a source goes offline or comes back, a product is missed, with the same rule as the scene, `isMissed`), marked on the timeline and reached by click or PageUp/PageDown; the playback clock (`tick`, `seek`, `step`, `playFrom`) is pure. The replay buffer (ADR 0011) is a `Recorder` in replay-buffer mode (`Recorder.replayBuffer()`, `windowMs` = `REPLAY_BUFFER_MS`, 60 s before its newest message, whole blocks dropped), created in `App.tsx` next to the `GatewayStore` and fed every message from page load; `snapshot()` gives the kept blocks as an ordinary recording starting at 0 (events, products and snapshot times found again from the blocks), behind the icon button right of Record. `player.ts` plays a recording as a `SceneFeed`, the interface the 3D view and the inspector read live data through.
- Tests live only at the seams: gateway tests drive an `InMemoryPlc` (or several, combined) and assert on emitted messages; web tests call `buildScene`, `buildMachineScene`, the recording (any moment, config changes, product registers, timeline events, limit, file round trip), the replay buffer's snapshot and the playback clock, `ProductHistory`, `metrics`, `parseViewSettings`, the inspector's generic state values and tables (`stateRows`); they also check the pointer picking in `src/scene/picking.ts` (tap or drag, nearest snap point on screen; mouse and touch tolerances). The API docs are tested at the gateway seam (`api-docs.test.ts`: every field described, examples valid against the JSON Schema, `/docs` served with and without a web app). Small gateway seams for deployment are tested too: `resolveGatewayOptions` (flags, config file, default paths packaged vs. repo), `bridgeLaunch` (exe vs. dll), the bridge process (a node stand-in that dies: the request fails, the next one starts a new bridge) and `/health`. Rendering itself is not unit tested: the browser tests (`apps/web/e2e/`) drive the built app against the simulator through the main flows (scene and tree, side panels incl. reload, camera views, layers / hidden components / camera kept across a reload, measuring two points, record / play / seek / save / open, replaying the last minute, jumping to a fault on the timeline, a selected product's history and the metrics in the inspector, the API link opening `/docs` without broken anchors) and check that the built app is split into parts of at most 800 KB (`manualChunks` in `apps/web/vite.config.ts`: three, react-three, react, vendor, app). The package is checked by a smoke run.

## TwinCAT MCP

- TwinCAT projects may be closed. If a call fails because no XAE is running (`find_projects` lists nothing, or RPC 0x800706BA), open the solution yourself: start `C:\Program Files\Beckhoff\TcXaeShell\Common7\IDE\TcXaeShell.exe "plc\RPP_Visu.sln"`, wait until the window title shows `RPP_Visu`, then call `initialize`.
- If a TwinCAT MCP call has not answered after 5 minutes, do not keep waiting. Retry it once (after `initialize` again). If it hangs again, try another way: a different tool for the same goal, smaller steps, or check whether XAE shows a modal dialog and ask the user to close it.
